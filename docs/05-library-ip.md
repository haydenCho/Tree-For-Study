# 도서관 공인 IP와 프록시 설명

## 질문에 대한 답
네. 도서관 Wi-Fi에 연결한 기기에서 '내 IP'로 보이는 공인 IP를 등록하는 방식으로 시작할 수 있습니다. 다만 그 값 하나가 모든 스터디원의 우리 서비스 요청에서 항상 같은지는 현장 확인이 필요합니다. 네이버 IP 조회는 참고, 최종 기준은 우리 서비스 서버가 관측한 실제 클라이언트 IP입니다.

## 네트워크 흐름
노트북의 사설 IP(예: 192.168.x.x) → 도서관 공유기/NAT의 공인 IP → 인터넷 → EC2의 Caddy → FastAPI.
단순한 IPv4 공유기 환경에서는 여러 기기가 하나의 공인 IP를 공유합니다. 도서관은 여러 회선/망/출구를 쓸 수 있고, IPv6는 기기별 주소가 다를 수 있습니다. VPN·프라이버시 릴레이·모바일 데이터 우회도 영향을 줍니다. 그래서 휴대폰·PC에서 동일 Wi-Fi로 직접 확인합니다. 기관 전체가 공유하는 IP라면 그 IP만으로 특정 도서관 건물에 있음을 증명할 수는 없습니다.

## 프록시는 무엇인가
Caddy는 서비스 앞에서 HTTPS를 받고 React 파일을 제공하거나 /api 요청을 FastAPI로 전달하는 역방향 프록시입니다. 도서관에 별도 프로그램을 설치하는 것이 아닙니다. FastAPI 입장에서는 바로 앞에서 접속한 Caddy의 내부 주소가 보일 수 있어, Caddy가 원래 사용자 주소를 X-Forwarded-For 등 전달 헤더로 알려 줍니다.
아무 사용자가 임의로 '나는 도서관 IP'라는 헤더를 보낼 수 있으므로, 앱이 헤더 첫 값을 그대로 쓰면 안 됩니다. Caddy는 직접 받은 외부 접속 주소를 기준으로 헤더를 정리하고, FastAPI/Uvicorn은 지정한 Caddy 연결에서 온 전달 헤더만 신뢰합니다. Caddy 주소를 도서관 허용 IP로 등록하는 것이 아닙니다.
배포 초기에는 인터넷→Caddy→FastAPI 한 단계로 단순화합니다. FastAPI 포트와 DB 포트는 외부 공개하지 않습니다. trusted proxy 목록에는 검증된 프록시 주소/격리된 전용 네트워크만 넣고 임의의 전체 '*'를 기본으로 쓰지 않습니다. Docker 프록시 주소/네트워크가 재생성될 때 설정도 검증해야 합니다. CDN/ALB를 앞에 추가하면 신뢰 체인을 별도로 재검토합니다.

## 현장 설정 절차
1. 운영자 PC를 도서관 Wi-Fi에 연결하고 VPN을 끈 상태로 네이버 내 IP를 참고합니다.
2. 우리 서비스 운영자 설정의 '현재 접속 IP 확인'에서 서버가 본 값을 확인합니다. 전체 사용자에게 공개하는 API가 아닙니다.
3. 해당 IP를 도서관 목록에 등록하고 새 집중 세션의 '도서관 장식 적용' 안내를 확인합니다.
4. 다른 PC/iPhone/Android에서도 동일 Wi-Fi로 인식되는지 확인합니다. 서로 다르면 운영자가 추가 주소를 검증해 등록합니다. 확인하지 않은 큰 CIDR 범위를 임의 등록하지 않습니다.
5. 다음 방문일에도 확인합니다. 변경된 공인 IP는 목록을 갱신합니다. 통신사망에서 도서관으로 인식되지 않는지도 확인합니다.

## 새 정책
POST /api/sessions 시점에만 판정하고 session.library_at_start에 저장합니다. 시작 전 화면 안내는 참고, 시작 요청이 최종 판정입니다. 이후 네트워크 변경/재개/종료 IP는 재판정하지 않습니다. 성공하면 그 세션의 모든 나무에 장식, 포기하면 회색 시듦만 적용합니다. 위치 인증이 아닌 현장 시작 보너스입니다.
